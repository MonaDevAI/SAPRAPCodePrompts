# Worked example: purchase-order application

The root [configuration](../rap-project.json) describes a synthetic custom purchase-order tracker. It does not create, wrap, or update SAP's standard purchase-order business object.

## Business model

| Field | Type | Behavior |
| --- | --- | --- |
| `PurchaseOrderNumber` | String, 20 characters | Required business identifier; not the technical UUID key |
| `SupplierName` | String, 80 characters | Required free-text supplier name; not a master-data integration |
| `OrderDate` | Date | Required |
| `NetAmount` | Amount, precision 15 / scale 2 | References `CurrencyCode` |
| `CurrencyCode` | SAP currency key | Required |
| `Status` | String, one character | Required; `N`, `A`, or `C`; defaults to `N` |

Technical UUID, audit, concurrency, and draft fields are generated by the backend template. Status values demonstrate validation/value help, not an implemented approval workflow.

## Generate the transactional application

Keep `target.mode` at `source-only` for an initial local run. Ask:

```text
Use the sap-rap-development skill with rap-project.json.
Generate the list report and object page, including any missing RAP backend.
Continue through all available checks and report what requires SAP access.
```

Expected output below `generated/purchase-orders`:

- `backend/`: persistence, CDS, behavior, metadata, service sources, and object inventory.
- `app/`: one Fiori elements application with list-report and object-page targets.
- `GENERATION-REPORT.md`: actual checks, assumptions, and import/activation/startup steps.

This is the expected output contract, **not a checked-in generated app or evidence of an SAP test run**.

## Add dashboards without duplicating the backend

In the same workspace:

```text
Use the sap-rap-development skill with rap-project.json.
Generate the overview page. Reuse the purchase-order backend already generated.
```

This creates `overview/` with a recent-orders list card and amount-by-status chart card when the target supports the required features. The chart card requires real analytical service support, even though the other card only needs a list.

```text
Use the sap-rap-development skill with rap-project.json.
Generate the analytical page. Reuse existing backend objects and analytics support.
```

This creates `analytics/` and any missing read-only analytical service objects. The dimension `CurrencyCode` prevents backend grouping from collapsing different currencies; the chart also needs a single-currency filter or a supported split presentation.

## Acceptance fixture

Use the synthetic records in [purchase-orders.sample.json](purchase-orders.sample.json) for local mocks or an explicitly authorized test-data setup. Do not automatically insert them into an SAP system.

Expected net-amount groups:

| Status | Currency | Net amount |
| --- | --- | --- |
| N | USD | 150.00 |
| A | USD | 200.00 |
| N | EUR | 80.00 |

The application must not display `430.00` as a meaningful single-currency total.

Focused scenarios:

1. Filter `Status=N`; the two USD records and one EUR record remain.
2. Filter `Status=N` and `CurrencyCode=USD`; the amount aggregate is `150.00`.
3. Omit a required supplier or use `Status=X`; server-side validation rejects the change.
4. Create/edit a draft and cancel; no unintended activation occurs.
5. Open an existing instance from the list; its object-page groups and currency display correctly.

## Adapt it

For another business entity, update `project.title`, `entity`, `entitySet`, `shortName`, and `appId`; replace the business fields; then update the field references under `ui`. Keep the prefix/short name unique in the target package.

If your model has no analytical measures, omit `ui.analytics` and remove overview chart cards, or omit `ui.overview` entirely. List-report and object-page generation does not require an analytical measure. The analytical template must ask for meaningful dimensions/measures before generating analytics rather than inventing one.
